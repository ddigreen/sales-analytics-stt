# Data contract and metric definitions

This is a proposed MVP contract, revised in SASTT-4. No client schema has been obtained and no backend is implemented. The rules below are implementation decisions proposed for teammate review; they are not evidence of a deployed system.

CSV sales import fields: source_system (nonempty string), external_deal_id (stable within that source), deal_id (internal immutable identifier), representative_id (authorized internal ID), opened_at (ISO 8601 with offset), closed_at (nullable ISO 8601 with offset), outcome (open, won or lost), amount (nonnegative decimal or blank), currency (ISO 4217 code or blank). Require closed_at for won and lost. Invalid outcome codes, negative amounts, duplicate conflicting IDs and naive timestamps require correction. Store time in UTC and render the user's selected timezone, initially Asia/Almaty. Never aggregate amounts across currencies without a documented conversion source and date.

Call manifest fields: source_system, external_call_id (stable within source), call_id (internal immutable identifier), deal_id (foreign key), representative_id, recorded_at (ISO 8601 with offset), declared_language (ru, kk, mixed or unknown), authorization_ref (restricted reference), audio_sha256 and storage_object_id. Authorization evidence itself is stored privately. A deal can have many calls; each call belongs to exactly one deal. An unknown or conflicting link is quarantined in a private validation preview; it is never silently guessed or accepted as a production Call. Reimports use unique (team_id, source_system, external_deal_id) or (team_id, source_system, external_call_id) and a canonical row hash for idempotency. Identical rows are skipped; changed metadata requires explicit update confirmation and a revision event. Equal external IDs in different sources or teams are independent records. A conflicting mapping within the same key is rejected rather than overwriting another record. Internal immutable IDs remain unchanged.

Core entities: User, TeamMembership, Deal, Call, ImportBatch, ProcessingJob, JobOutbox, TranscriptVersion, Segment, ExtractedItem, ReviewRevision and AuditEvent. An unprocessed Call has no current TranscriptVersion; a processed Call has at most one current version and may have historic or candidate versions. A Segment belongs to exactly one version. An ExtractedItem references that version and its supporting segment IDs; approval is invalidated when its evidence changes. ProcessingJob stores attempt count, status, error code and the recovery fields specified below. AuditEvent records actor, action, object ID and time without unnecessary transcript content.

Metrics: eligible closed deals are distinct deals whose outcome is won or lost and closed_at lies within the selected reporting period. Win rate is won / (won + lost); if the denominator is zero display Not available. Call counts use recorded_at and distinct call_id; display the different period basis clearly. Open deals are not lost. Won amount sums known won amounts separately for each currency; no amount is inferred from speech. Objection prevalence is the number of reviewed calls containing a particular reviewed objection divided by calls reviewed in the same cohort; it is not a population rate. Filters apply role permissions before aggregation. Synthetic prototype numbers illustrate interaction only.

Stable join IDs and data lineage are engineering requirements. A public telemarketing dataset without audio cannot be paired to unrelated speech recordings to create supposedly real joined observations.

## Role permission matrix

| Action | Salesperson | Manager | Analyst | Administrator |
|---|---|---|---|---|
| Import and link deals and calls | Own records | Assigned team | No | No unless separately granted a business role |
| Read audio and transcripts | Own calls | Assigned team | Only a separately granted authorized research subset | No inherent content access |
| Correct and review extracted items | Own calls | Assigned team | Only explicitly granted review subset | No inherent review right |
| View and export analytics | Own scope | Assigned team | Authorized deidentified dataset | Configuration metadata only |
| Request call deletion | Own records via approved workflow | Assigned team via approved workflow | No | Execute authorized retention and deletion job without browsing content |
| Assign roles and retention policy | No | No | No | Yes with audit |

All grants are team scoped. Default deny applies to unlisted actions and direct object access. Privileged maintenance does not silently grant a business content role. A multi role user receives only explicitly assigned content scopes; test intersections and cross team denial.

## Import ownership and atomic application

The authenticated session and active TeamMembership determine team_id; a CSV field, URL parameter or request body cannot grant a team scope. Every business entity, import batch, job and outbox event carries its team. Use same-team foreign keys for Call to Deal, representative membership, transcript versions, segments and evidence. An authorized uploader must also have permission for the referenced representative and deal. UUIDs and hidden UI controls are not authorization.

Internal deal_id and call_id are generated by the server for new records. A client may reference an existing authorized internal ID after resolving a source key, but cannot assign or move it. source_system names a registered import-source namespace within the team, not an arbitrary label that bypasses duplicate detection. External IDs are opaque, case-sensitive strings: retain leading zeroes, reject empty or surrounding-whitespace IDs, and do not fuzzy-match them. A call manifest can resolve a deal using (deal_source_system, external_deal_id); if both that key and deal_id are supplied they must identify the same authorized deal. Cross-source links require these explicit fields. A changed link requires a separately confirmed relink with a revision event and analytics invalidation.

An import has two steps: a private validation preview and an explicit apply. The preview lists row numbers and stable error codes, proposed inserts, identical skips, confirmed-update candidates and unresolved links. Reject the entire apply if any row remains invalid, conflicting or unauthorized. Correct and revalidate first; the MVP does not silently import a valid subset. Duplicate identical keys within a batch collapse to one accepted operation with a reported skip; different payloads for one key block the batch. Apply deals, links, revisions and the batch result in one database transaction. Unique constraints arbitrate concurrent imports; recheck authorization and expected record revisions at apply time. A stale preview returns 409 and requires revalidation, with no business-data writes.

The import idempotency key is scoped by (team_id, actor_id, operation, key) and binds the validated payload hash and schema version. The same key and payload returns the stored batch result; a different payload with that key returns 409. The row hash uses a versioned canonical serialization of validated fields (UTC instants, exact decimal values, explicit nulls and source keys); preserve the original private file checksum separately. Formatting-only changes are not business updates. A changed existing row without confirmation returns UPDATE_CONFIRMATION_REQUIRED. A confirmed update includes expected_revision and creates an old/new revision without resetting transcript review history. Audio bytes are immutable for an accepted call: a checksum change on the same call key is rejected as AUDIO_REPLACEMENT_REQUIRES_REVIEW; an audio replacement/version policy must be agreed before that operation is implemented.

Use exact decimals, never binary floating point, for monetary calculations. Reject NaN, infinity and negative amounts. A known amount requires a validated currency; a missing amount is null, not zero. A won deal with unknown amount still contributes to win rate, and its omission from the monetary sum is reported as missing-amount coverage. Blank/unknown source outcomes are validation errors requiring correction, never coerced to lost or open. An absent outcome in an incomplete/restricted UI response is displayed as unknown and excluded from closed-deal metrics. open requires closed_at=null; won/lost require closed_at>=opened_at. Calls need not precede deal closure: follow-up calls are legitimate.

## Reporting cohorts and time boundaries

Convert the selected local date range using its IANA timezone to a half-open UTC interval [start, end). For example, 21 October 2026 in Asia/Almaty is [2026-10-20T19:00:00Z, 2026-10-21T19:00:00Z). Reject impossible dates and timestamps without an offset. Do not hardcode a fixed offset for all dates or timezones.

Authorize records before filtering or aggregation. Sales metrics start from Deal, not from an inner join to Call. With all languages selected, authorized deals without recordings remain eligible. With a language filter, select deals using EXISTS over authorized linked calls of that declared language, independently of the call-volume date window; never multiply a deal by matching calls. Deal representative filters use Deal.representative_id; call-volume filters use Call.representative_id. Different call/deal owners are allowed only when explicitly authorized, and the response labels the two bases. Current open pipeline is a snapshot and must not be presented as historical period flow. Return metric-definition version, timezone, UTC boundaries, filters, currency groups, missing-amount counts and a data/review revision token with analytics and exports.

For objection prevalence, define a reviewed call as one whose objection review for the current transcript version is complete, including an explicit reviewed finding of no objections. Reviewing one item does not complete a multilabel call review. Count each call at most once per category, include reviewed negative calls in the denominator and return Not available for an empty denominator. Next-action approval is separate. Transcript edits or version promotion invalidate affected current review completion; historic approvals remain historic. These semantics are for the future API; the mockup shows counts only.

## Scoped API access

Every list, search, detail, job-status, retry, evidence, audio, review, export and deletion endpoint checks both action and object scope. Unauthenticated requests return 401. Return 404 for an object outside the caller's visible scope, including guessed nested IDs; return 403 for an action disallowed on an otherwise visible object. Do not leak foreign-team existence through counts, pagination, errors, job IDs or download links. Combining a manager role in team A with a salesperson role in team B does not confer team-B manager access. A research read grant does not imply a review grant or permission to export identifiable data. Recheck grants when serving stored exports or issuing any object download capability.

Audio access uses an authenticated API streaming proxy that checks current scope and deletion state for each request, including range requests. Object keys and storage endpoints are not public URLs; browsers never receive storage credentials. Workers use a separate minimum-permission service identity and load team/job/call relationships from the database. Queue payloads carry job identifiers, not audio, transcript text, signed URLs or authorization documents. Error messages use stable content-free codes.

## Durable processing and safe retries

PostgreSQL is the authoritative job/result store; Redis transports notifications. In one transaction, the API creates the ProcessingJob and JobOutbox event after the private upload has been validated and finalized. Return 202 with job_id and queued status only after commit. An outbox dispatcher publishes job IDs and marks delivery; if publish succeeds but marking fails it may publish again. A recovery scan republishes due queued jobs and handles expired processing leases, so a committed job is not stranded by an API crash or broker loss. Dispatch retries do not consume inference attempts.

A processing request binds (team_id, call_id, input checksum, pipeline configuration hash, requested generation). Repeated idempotency keys return the same job; a deliberately new processing generation is an explicit authorized action. A worker transaction conditionally claims a due queued job, increments attempt_count, and assigns a lease token, lease expiry and heartbeat. Only the current unexpired token may commit results. Duplicate deliveries cannot claim a running/completed job or consume another attempt. Bounded processing timeouts and a recovery scan fence off a stalled worker before another attempt starts.

The public processing states are queued, processing, completed and failed. A transient failure or expired lease returns processing to queued with a persisted next_attempt_at if attempt_count<3; otherwise it becomes failed. Thus there is one initial attempt and at most two automatic retries, including crash recovery. Permanent invalid audio, authorization failure or unsupported configuration fails without automatic retry. Apply bounded exponential backoff with jitter; choose host-specific timeouts at integration. A manual retry after terminal failure is a new, audited generation with its own idempotency key and budget. Broker redelivery is never treated as permission to reset the budget.

Commit the validated transcript, segments, draft items and completed job status in one transaction, uniquely keyed to the producing job. A crash before commit leaves no published partial result; a crash after commit and before acknowledgement is a no-op on redelivery. Maintain expected_current_version when scheduling: a valid result may be saved as a candidate, but may become current only by a conditional version update. If a reviewer has edited/promoted a version meanwhile, preserve that version and retain the new candidate for explicit review. A rerun cannot overwrite approved corrections. Configure and test Celery acknowledgements, worker-loss behavior, task timeouts and Redis visibility timeout against this protocol; defaults alone do not guarantee recovery.

## Transcript and review integrity

TranscriptVersion is immutable and records call_id, team_id, parent_version_id, input checksum, model name/revision, configuration hash, language strategy, duration and processing timings. Human transcript or speaker-label edits create a new version with actor/time provenance. A Segment has version_id and satisfies 0<=start<end<=duration. Evidence references use (team_id, call_id, version_id, segment_id); database foreign keys or equivalent transactional validation must prevent another call/version's segment from being cited. At least one valid supporting segment is required for an item to be confirmed; existence alone does not establish semantic truth, which still requires source review.

Review writes include expected transcript version and item revision; stale writes return 409 without overwriting another review. Store per-item draft/reviewed/corrected status and a private ReviewRevision containing old/new values, reviewer, time and evidence IDs. New versions create new draft items; historic review is never silently copied to changed evidence. Approval of one objection does not approve other objections or next actions. Workers can create drafts, never human approvals or CRM outcomes.

## Private storage and deletion races

Finalize uploads under opaque private keys with server-verified media type, byte length, decoded duration and SHA-256. An authorization_ref must resolve to a valid private authorization basis before processing. Reconcile failed/abandoned temporary uploads and database/blob mismatches. Retention duration is a policy setting awaiting the data owner's agreement; the example 30 days is not evidence of permission or an agreed legal period.

On an authorized deletion, mark the Call deleting immediately and deny content reads and new processing/review. Persist the deletion job transactionally, invalidate processing leases and ensure every result commit rechecks the tombstone; a late worker cannot recreate removed derivatives. Cleanup is idempotent and retried durably until audio, all versions, segments, items, revision text, temporary files, indexes and export caches are removed. Keep only a content-free deletion/tombstone record sufficient to reject stale work and prevent silent resurrection by reimport; any later re-creation requires a fresh authorized workflow. FR13 active cleanup is due within 24 hours; backup expiry is at most 30 days. Restore procedures must replay deletion tombstones before exposing restored data. Previously downloaded exports need an owner policy; do not claim remote copies were erased.

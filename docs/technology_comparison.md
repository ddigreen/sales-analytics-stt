# Technology choices for the proposed prototype

**Decision basis.** Assume a small student team, prerecorded consented/demo calls, CSV sales imports, Russian/Kazakh/mixed speech evaluation, and a modest pilot workload. These are planning assumptions, not user-confirmed infrastructure facts. Choices below are engineering judgments based on documented capabilities, not measured speed, accuracy, or cost rankings. Official sources accessed **21 October 2026**.

| Decision | Alternative A | Alternative B | Alternative C | Proposed choice and reason |
|---|---|---|---|---|
| Backend API: Python model integration, API contracts, administrative work | **FastAPI:** Python types/Pydantic validation and automatic OpenAPI documentation; application must supply its data/admin structure [T1] | **Django:** ORM, authentication-oriented admin interface and conventional database application structure; useful if record administration dominates [T2] | **NestJS:** TypeScript/Node.js modular application structure; appropriate for a TypeScript team, with local Python ASR typically kept in a separate process/service [T3] | **FastAPI**, provisionally: share Python types and tooling with ASR/evaluation and expose an inspectable API. Revisit if the team already knows another framework well. |
| Database: linked sales records, transcript metadata, deployment effort | **PostgreSQL:** relational constraints plus indexed JSONB for variable extraction metadata; requires a database service [T4], [T5] | **SQLite:** embedded SQL with low setup effort; one writer at a time, which may suffice for a single-user demonstration [T6] | **MongoDB:** flexible document schema with embedded/referenced relationships; sales joins require deliberate document/access-pattern design [T7] | **PostgreSQL** for shared prototype: represent customers, deals, calls and outcomes with explicit keys; store optional model outputs in JSONB. SQLite remains a valid minimal offline demonstration option. |
| Speech recognition: deployment control, language testing, resource requirements | **Local Whisper:** downloadable multilingual models; model sizes trade memory for speed/accuracy; performance varies across languages [T8] | **Azure Speech:** hosted real-time/batch APIs and custom speech options; feature availability varies by language and region [T9] | **Google Cloud STT:** hosted asynchronous file recognition; language/model/region feature matrix, including Kazakh models [T10], [T11] | **Local Whisper baseline**, using a model size selected after hardware profiling; keep an ASR adapter so a hosted provider can be compared later. Local execution after model download supports repeatable versioned evaluation. Cloud use requires credentials, transfer approval and a budget. No accuracy winner claimed. |
| Processing: user responsiveness, failure handling, operational complexity | **Synchronous request:** fewest components; caller waits for full transcription, so suitable only for short smoke tests | **FastAPI BackgroundTasks:** runs after returning a response in the application process; suitable for small in-process work [T12] | **Celery worker + broker:** dedicated workers distribute queued tasks, with task-state/retry mechanisms that require configuration and extra services [T13] | **Celery worker + Redis broker** in the target design: API returns a job ID; database records queued/running/completed/failed status. For the first offline experiment, use a CLI batch runner; add queue infrastructure when integrating the web UI. |

**Practical design.** Keep raw audio in local private file/object storage and place references/checksums in the database. Store timestamps, language, model identifier, model configuration, transcript version, and the originating call/deal identifier. Treat extraction and summary fields as derived evidence that users can inspect and correct. Add job idempotency and bounded retries so rerunning a failed job does not duplicate calls or overwrite approved corrections.

**Decision gates.** Measure word/character error rates by language, entity/objection extraction precision and recall, end-to-end processing time, and KPI correctness on fixed examples. Record hardware and audio duration. Compare cloud ASR only on the same consented audio and scoring protocol; quotations and public language lists do not establish domain accuracy. If local processing fails the team's measured resource/time constraints, choose a hosted adapter after checking the exact locale, region, feature matrix and cost. Synthetic sales outcomes may validate calculations and interfaces, but cannot establish conversion prediction or causal sales improvement.
